# 问题缓存机制方案（问答结果复用，提速 + 省 token）

## 1. 背景与目标

现状：每个问题都走完整 `intent → tool → observe → extract → summarize → critic` 工作流，即使问题与之前完全一样，仍会：
- 再次调用 LLM 做意图分析 + 汇总（**烧 token**）
- 再次查数据库 / 检索知识库 / 联网（**慢、重复占用外部服务**）

若用户在会话里反复问同一个问题（例如「固始县有几家采砂场」问了两遍），目前是**零复用**，每次都从零跑一遍。

目标：新增**问答结果缓存**，命中「之前问过且未失效」的问题时**绕过整个工作流直接回放历史结果**，让这类问题：

1. **更快**（毫秒级返回，不再现场分析/查库）
2. **省 token**（不调用意图/汇总 LLM）
3. **省外部调用**（不再重复查 DB / 知识库 / 联网）

> 前提（已核实）：项目已有 `run_store`（`runs/run_events/run_checkpoints`）与 `idempotency_keys` 表、`RunEngine.resume` 断点续传骨架。缓存机制**复用**这套存储与 SSE 事件回放通道，**不推翻**现有流程，只做**命中早退**。

---

## 2. 现状盘点（可复用点）

| 能力 | 现状 | 位置 |
|---|---|---|
| 会话级 run 持久化 + 事件流（`seq` 游标回放） | ✅ | `run_store.py` |
| 工具副作用幂等（同 run 内去重） | ✅ | `run_store.py::idempotency_keys` |
| SSE 事件流回放 / 断线补拉 | ✅ | `event_bus.py`、`chat.py::chat_stream` |
| 前端逐轮从 DB 读历史、fire-and-forget 压缩 | ✅ | `chat.py` 阶段4 |
| **跨 run 的问答结果缓存** | ❌ 缺 | — |

关键差异：现有 `idempotency_keys` 是**同一个 run 内**（`PRIMARY KEY(run_id, step_id)`）防重放；本方案是**跨 run、跨请求**复用整个回答。

---

## 3. 方案概览（分层缓存）

按「命中粒度从小到大、收益从大到小」分三层，分期落地：

| 层 | 缓存的是什么 | 命中收益 | 复杂度/风险 | 分期 |
|---|---|---|---|---|
| **L1 响应级缓存** | 整条「问题→最终结果」（response + 地图命令 + 图表 + 报告地址） | **最大**：完全跳过工作流，零 LLM、零工具调用 | 低（键 = 归一化问题哈希 + 失效控制） | **P0** |
| **L2 工具结果缓存** | 单次工具的返回数据（只读工具：DB / 知识库 / 联网） | 中：同参数工具不再重复外部调用 | 中（需考虑数据时效/会话隔离） | **P1** |
| **L3 语义缓存**（可选） | 语义相似的问题（embedding 近邻） | 中：近似问题也能命中 | 高（相似度误命中风险，需评审） | **P2** |

本方案**P0 先做 L1**（最贴合「之前问过的问题不重复跑」的诉求），L2/L3 作为后续可选扩展。

---

## 4. L1 响应级缓存（P0，核心）

### 4.1 缓存键设计

命中判定要足够准，避免「看似同问其实不同」误命中。键采用**分层归一化**：

```
normalize(query, session_ctx) →
    base = strip_punctuation(lower(trim(query)))        # 去标点/空白/大小写归一
    key  = sha256(base + "|" + session_workspace_fp())  # 加入工作区指纹
```

- **问题归一化**：去首尾空白、全半角归一、去常见标点、折叠连续空白，避免「固始县有8家」vs「固始县有 8 家」这类纯排版差异判不中。
- **工作区指纹 `workspace_fp()`**：由当前会话已加载的图层/产物摘要生成。**同问题但工作区已变化（如用户新加载了图层）→ 键不同，不误命中旧结果**。指纹可用 `workspace_state.build_summary(session_id)` 的哈希。

> 若某会话问题与工作区强相关，可只对「地图/加载类」意图纳入工作区指纹，纯知识问答类忽略指纹，提高命中率（P1 细化）。

### 4.2 命中早退（接入点：`chat.py::chat_stream`）

在 SSE 入口、**进入 RunEngine 之前**插入缓存检查：

```
请求进入 → 归一化 query → 查 response_cache
 ├─ 未命中 → 走原有 RunEngine.start()，结束后写缓存
 └─ 命中且未失效 →
     1. 用存储的结果重放事件流（status → final），前端体验与真实执行一致
     2. 命中计数 +1
     3. 直接返回，不创建 run、不调用任何 LLM/工具
```

前置顺序（放在当前 `pending resume` / `recover_session` 判定**之后**、`engine.start` **之前**，避免破坏既有续传逻辑）：
1. 有 pending 待确认 → 走原 resume（用户介入场景不该被缓存顶掉）
2. 无 pending → `recover_session` 续传（崩溃恢复优先）
3. **仍无任务** → 查缓存 → 命中早退 / 未命中才 start

### 4.3 数据模型（新增 `response_cache` 表，复用 sessions.db）

```sql
CREATE TABLE IF NOT EXISTS response_cache (
    query_hash   TEXT PRIMARY KEY,      -- 归一化键
    session_id   TEXT NOT NULL,         -- 归属会话（隔离/清库用）
    query        TEXT NOT NULL,         -- 归一化原文（审计/调试）
    result_json  TEXT NOT NULL,         -- 完整 final result（response/map_commands/charts/intent_info…）
    hit_count    INTEGER NOT NULL DEFAULT 0,
    created_at   TEXT NOT NULL,
    last_hit_at  TEXT NOT NULL,
    ttl_seconds  INTEGER NOT NULL,      -- 缓存有效期
    active       INTEGER NOT NULL DEFAULT 1
)
CREATE INDEX IF NOT EXISTS idx_response_cache_session ON response_cache(session_id)
```

沿用 `run_store` 幂等建表风格（`CREATE TABLE IF NOT EXISTS` + 存量库自动补）。

### 4.4 失效策略

| 策略 | 做法 |
|---|---|
| **TTL** | 缓存记录带 `ttl_seconds`（默认可按意图区分：知识问答 1h / 数据查询 10min / 地图 5min），超时视为缺省 |
| **显式清除** | 会话内新增工具副作用（外部写操作）或工作区**关键变化**时，清除该会话相关缓存 |
| **会话隔离** | 键含 session 或按 session 过滤，A 会话的命中不影响 B 会话 |
| **主动更新** | 每次真正执行后写回缓存（`INSERT OR REPLACE`），保证库里是最新一次的真实结果 |

### 4.5 省 token 量化（估算）

设单问题平均消耗 = 意图分析 `T1` + 汇总/评审 `T2` + 工具调用。
- **知识类**复用：省 `~T1+T2`（约 1~2K token/次）
- **数据/地图类**复用：省 `~T1+T2 + 外部查询`（更多）
用户反复问同一问题越频繁，收益线性放大 → 对高频重复场景明显。

## 5. L2 工具结果缓存（P1，可选增强）

在 L1 未命中、真正执行时，缓存**只读工具**的单次返回数据，供「同参数」复用，避免重复外部调用：

```sql
CREATE TABLE IF NOT EXISTS tool_cache (
    tool_name   TEXT NOT NULL,
    params_hash TEXT NOT NULL,
    session_id  TEXT NOT NULL,           -- 可空=全局只读
    result_json TEXT NOT NULL,
    created_at  TEXT NOT NULL,
    ttl_seconds INTEGER NOT NULL,
    PRIMARY KEY (tool_name, params_hash, session_id)
)
```

- 接入点：`RunEngine._invoke_step` 内，只对 `postgresql_tool / knowledge_base_tool / web_search_tool` 等**只读**工具命中/写入。
- 命中判定：`tool + normalize(params) + session` 组合哈希。
- 注意：DB/知识库数据有时效，TTL 要比 L1 更短（数据类默认 60s~5min）。
- **不做**：地图/三维命令、报告生成等有副作用的工具不进 L2。

---

## 6. L3 语义缓存（P2，可选）

用问题向量（embedding）做近邻检索，命中「语义等价」的问题（如「固始县采砂场数量」 vs 「固始县几家砂石厂」）。

- 复用项目已有向量检索基建（`kb_milvus` / `llama_index_storage`）。
- 风险：相似≠等价，误命中可能回答偏题，需**高相似度阈值 + 人工评审开关**。
- 建议 P2 且默认关闭，仅对知识问答类启用。

## 7. 模块改动清单

| 文件 | 动作 |
|---|---|
| `agents/cache_store.py` | **新增**：`response_cache`/`tool_cache` 建表 + 查询/写入/失效 API |
| `agents/query_key.py` 或并入 `context_route.py` | **新增**：`normalize_query` / `hash_query` / `workspace_fp` |
| `routers/chat.py` | `chat_stream` 命中早退；结束时写缓存 |
| `agents/cache_manager.py` | **新增**：读写/命中计数/失效编排（薄封装） |
| `tests/test_cache.py` | **新增**：key 稳定性/归一化、TTL 失效、命中计数、工作区指纹 |

不改：`run_store` 既有表结构；`RunEngine.start/resume`（缓存只做入口早退，不侵入执行）。

---

## 8. 明确不做 / 边界

- **不**混淆「跨 run 复用」与「同 run 幂等」：两者各自独立，缓存不破坏断点续传。
- **不**对带副作用的请求开缓存（写库/生成报告/发命令类默认跳过）。
- **不**做全自动语义缓存（P2 才考虑，默认关）。
- 命中返回的是**历史最终结果**，若底层数据已变，靠 TTL + 工作区指纹控制时效，不保证绝对"最新"。

---

## 9. 分期实施建议

- **P0（最小可用）**：`response_cache` + `normalize_query` + `chat.py` 命中早退，仅知识/数据类意图可缓存。
- **P1（增强）**：`tool_cache` 只读工具复用 + 工作区指纹细化（地图类） + 会话级失效。
- **P2（进阶）**：语义缓存（默认关）+ 命中统计看板（`hit_count` 趋势）。

每期独立可交付、可回滚；建议从 P0 开始。

---

## 10. 验证

1. 单元：`normalize_query` 对排版差异归一并得到稳定哈希；TTL 过期后不再命中；同问题命中计数递增；工作区变化后键不同不再误命中。
2. 单元：`response_cache` / `tool_cache` 建表幂等、读写在空库与存量库均正常。
3. 集成（可选）：同一问题连发两次 → 第一次走工作流、第二次**日志可见缓存命中且无 LLM/工具调用**；改动后同问题 → 新结果回写，旧缓存被替换。
4. 静态：确认缓存接入点在 `recover_session` 之后、`engine.start` 之前，不破坏既有 pending/续传逻辑。
