# 上下文路由协议 + 宕机断点续传 — 完整方案

## 1. 背景与目标

现有智能体是单请求内 `intent → tool → observe → extract → summarize → critic → confirmation` 的 LangGraph 有向图（[task_executor.py#L118-L154](agents/task_executor.py#L118-L154)），上下文经 `AgentState` 共享、由 `context_manager` 做预算/分层组装。长周期任务（多次工具调用、等待用户补参/确认）在系统宕机上缺少**显式契约**：

1. **上下文路由协议缺位**：`context_manager`（活进程内的预算/分层）与 `run_store`（SQLite 步骤持久化）是两套独立系统，没有统一契约说明「每个 stage 需要哪些上下文块、哪块必须持久化、续传时如何重建」。
2. **宕机检测缺位**：进程崩溃时 `runs.status` 停在 `RUNNING`，无 watchdog 标记为可恢复，恢复依赖前端重连后主动 resume。
3. **副作用幂等与事件重放**：`run_events` 有 `seq`，但工具步骤在 resume 重跑时的副作用去重无统一 key。

目标：
- 新增**上下文路由协议（ContextRoute）**，把「来源 → 路由 → 预算 → 持久化级别 → 续传重建」收敛成唯一契约，活流程与续传共用同一套 `route_for`。
- 在**既有** resume 骨架上补齐宕机检测、幂等重放、原子 checkpoint、跨进程恢复，让长周期任务在服务崩溃后能**自动识别为可恢复并从断点续传**。

> 关键前提（已核实）：项目**已存在**一套步骤级断点续传骨架（`run_store` 的 `runs/run_events/run_checkpoints` + `RunEngine.resume()`），且 **resume 依赖 `state_json` 而非 LangGraph `MemorySaver`**。本方案**不推翻、不重构**既有机制，只做增量补齐。

## 3. 上下文路由协议（ContextRoute）— 新增

新模块 `backend/agents/context_route.py`。

### 3.1 结构化上下文块
```python
ContextBlock:
  kind:        system | history | facts | workspace | tool_results
               | tool_summaries | critic_feedback | pending
  source:      static | sessions.db | fact_memory | workspace_state
               | run_checkpoints | context_manager
  durability:  EPHEMERAL | SESSION | CHECKPOINT
  budget_tokens: int            # 复用 context_manager 的 estimate_tokens
  priority:     int              # 复用优先级裁剪
  payload, ttl
```

### 3.2 路由表（stage → 块 + 预算 + 持久化级别）
| stage | 消费块 | 持久化级别 | 说明 |
|---|---|---|---|
| intent | system + history + facts + workspace | SESSION | 活进程内从 sources 现取 |
| tool / observe | 上一节点产物 + tool_results | CHECKPOINT | 步骤间落 checkpoints |
| extract | tool_results | CHECKPOINT | 产出结构化命令 |
| summarize | system + history + 裁剪 tool_summaries + critic_feedback | CHECKPOINT | 拼 LLM prompt |
| confirmation | pending + missing_params | CHECKPOINT | 与 resume 语义一致 |

### 3.4 唯一真相契约
所有 stage 的上下文「来源、预算、持久化级别」**只在这张路由表定义一次**。活流程与续传都调用 `route_for(stage, ctx)`。续传不是另写一套，而是「用存储的 state_json + 当前剩余步骤，重建本次 stage 需要的 blocks」。这样预算调整只改一处，活流程与续传行为天然一致。

## 4. 状态恢复 / 宕机断点续传补强

对着 §2 缺口逐个补齐（均为增量）。

### 4.1 宕机 watchdog（新增）
- `runs` 表幂等加列 `heartbeat_at TEXT`、`last_node TEXT`。
- 运行中每次工具步骤/事件落盘时更新 `heartbeat_at`、`last_node`。
- 判定规则（可配，默认）：
  ```
  status=RUNNING AND now - updated_at > STALE_AFTER (默认5min) → status=INTERRUPTED
  ```
- 触发器：进程内一个 `asyncio` 定时 watchdog；同时在「同 session 新请求进入」时做**懒检查**（把该 session 的历史 INTERRUPTED/RUNNING 残留 run 标记并转 RESUME）。两者都要，避免只靠定时器漏。

### 4.2 自动 resume 链路
1. 新请求带 `session_id`。
2. 查最近一条 run：若 `INTERRUPTED` 且存在有效 checkpoint → 标 `RESUMING`，走 `RunEngine.resume()`。
3. resume 内部：`store.load_checkpoint()` 载入 `state_json` → 用 `route_for(next_stage, ...)` 重建上下文 → 跳过已执行步骤（幂等 key 过滤）→ 从 `remaining_steps` 续跑（现有 resume 主路径不变，只在前置接入 watchdog 判定）。

### 4.3 副作用幂等 + 事件去重
- 新表 `idempotency_keys(run_id, step_id, params_hash, created_at)`，`PRIMARY KEY(run_id, step_id)`。
- 工具步骤执行前插入 key，成功后再提交结果；resume 时命中 key 的步骤**跳过重跑、复用已存结果**。
- 事件推送以 `run_events.seq` 为游标，`resume` 只推 `seq > 前端已送达` 的事件（沿用现有 `_emit`/`run_events`）。

### 4.4 原子 checkpoint + 定位
- `save_checkpoint` 单事务写：`UPDATE runs SET status,last_node,updated_at,heartbeat_at` + `REPLACE INTO run_checkpoints(state_json,updated_at)`。
- `last_node` 落盘，重启后一眼定位「断在哪一步」。
- `state_json` 升级为带版本的 `route_meta`（`{version, stage_cursor, remaining_steps, intent_result, tool_results[], idempotency_keys, pending, route: {stage→budget}}`），**兼容旧 state_json**（缺字段按旧语义解析）。

### 4.5 优雅停机（可选）
- 服务捕获 SIGTERM/SIGINT：把进行中 run 标 `INTERRUPTED` 并落一个 checkpoint（当前 state），保证重启后从断点续传而不丢。

## 7. 时序

### 正常流
```
请求 → 懒查 watchdog(无残留) → intent(route_for) → tool(执行+幂等key+checkpoint+heartbeat)
     → observe → extract → summarize → 完成 → status=COMPLETED, delete_checkpoint
```

### 崩溃—恢复流
```
进程崩溃(run 停在 RUNNING)
重启后同 session 新请求 → 懒检查: RUNNING 且超时 → INTERRUPTED
    → 找 checkpoint → RESUME
    → load state_json → route_for(next_stage) 重建上下文
    → 幂等 key 跳过已执行步骤 → recause remaining_steps 续跑
    → 只推 seq>cursor 的事件 → 完成后 COMPLETED
```

## 8. 边界与明确不做

- **不**把 LangGraph 换 SQLiteSaver / checkpointing 大规模重构（现有自定义 step 级机制更贴合，且已不依赖 MemorySaver）。
- **不**引入分布式队列 / Redis / 多实例编排；本方案按单进程多 run 设计（与现状 `run_store`/`MemorySaver` 一致）。
- **不**改 `context_manager` 公共接口；协议只做「路由 + 持久化映射」的编排层。
- 幂等仅覆盖**工具步骤**（只读 DB/检索天然安全；对外部写副作用才需要 key），不覆盖节点内纯计算。

3. 集成（可选）：起服务 → 发起一个需多步工具+补参的长 run → 模拟 kill 进程 → 重启 → 同 session 再发消息 → 断言自动转 RESUME 并从断点续跑、事件不重复。
4. 静态：grep 确认 `context_manager` 公共签名未变；`run_engine` resume 主路径改动仅在前置接入点。
